# 设计：单向版本化备份

本文记录 `dsh-vault-sync` 的架构决策与**为什么这样决策**。需求与价格表来自 `同步方案与 dsh 插件设计.md`（评审文档 1.0），实现按其"需要根据 paper 仓库插件的实际情况进行调整"的要求落在 Paper Library 的工程约定上。

## 1. 职责划分

| 关注点 | 归属 | 理由 |
|:--|:--|:--|
| 扫描、差异、上传、归档、核对 | 本插件 | 与调度、界面无关，可单独测试 |
| 系统级定时 | dsh-cron-scheduler | 已有 crontab 部署、headless 运行与结果归档；本插件不重复造调度 |
| 界面 | 无 | 备份是低频运维动作；CLI 与 JSON 报告足够，避免再养一套前端 |
| 文献库语义 | Paper Library | 本插件把文献库目录当作普通目录；`kind: paper-library` 只是标注，不是耦合 |
| 云存储规则 | 用户 / 控制台 | 生命周期、解冻、费用预警属于账号侧策略，插件不代理 |

**关键约束：单向。** 插件只读源目录，只写远端与管理状态目录。任何"远端更权威"的路径都不存在，因此不可能出现远端覆盖本地资料的事故。

## 2. 数据流

```
sources[].root ──扫描──> 本地清单(相对路径, 字节, sha256)
                              │
远端 listing ────────────────>├──规划(纯函数)──> upload / version / delete / skip
本地索引(上轮成功清单)────────┘        │
                                      ▼
                             执行：归档 → 临时前缀上传 → 校验 → 服务端复制到正式路径 → 删临时
                                      │
                                      ▼
                             索引仅在整源成功后推进；运行记录写 runs/<runId>.json
```

## 3. 决策与替代方案

### 3.1 自己实现 S3 客户端，而不是把 rclone 变成硬依赖

评审文档以 rclone 为引擎。实现上保留 rclone 通道（`engine: rclone` 或 `rcloneRemote`），但默认走内置 SigV4 客户端，原因：

- **无外部二进制依赖**：Harness 插件在用户机器上运行，缺 rclone 时不该整个功能不可用。本包运行时依赖为 0。
- **摘要元数据**：rclone 的 `lsjson` 不返回内容摘要，只能按大小判断，会把"同大小但内容已变"的文件长期当作未改动。原生通道把 sha256 写进 `x-amz-meta-sha256`，判定是精确的。
- **可核对**：没有摘要时 `verify` 只能如实报"未按摘要核对"，这是能力差异，不是实现取巧。
- **代价**：需要自己实现 SigV4。因此用 AWS 公开的 `get-vanilla` 测试向量做逐字节比对（见 `docs/validation.md`），并在进程内 S3 兼容服务端上端到端跑签名、分页、服务端复制、重试与错误映射。

### 3.2 版本化用 `--backup-dir` 语义，而不是 bucket 版本控制

- 保留 OSS 侧简化的前提：不需要开启版本控制，也不需要理解 version-id 语义；历史版本就是普通对象，任何工具都能列、能取。
- 归档 = **服务端复制**：不重新下载、不重新上传，带宽成本与本地 IO 都为 0。
- 代价：同一个文件同一天被改两次只保留最后一次归档（同日重复覆盖），因为版本键含日期。这是刻意的——版本区是"每日快照"，不是逐次变更日志；逐次日志交给 OSS 生命周期/审计，不在这里堆。

### 3.3 上传顺序：归档 → 临时 → 校验 → 正式

崩溃安全来自**顺序**，不是回滚：

1. 先把被替换/被删除的对象复制到 `versions/<日期>/…`；
2. 新内容上传到 `incoming/<runId>/…`，并 `head` 校验字节数与摘要；
3. 服务端复制到正式路径，删除临时对象。

第 1 步与第 3 步之间崩溃，最坏结果是"版本区有一份旧副本 + 正式路径暂时缺失"。下一轮规划发现远端缺失即重传，索引未推进，所以不会误判为已完成。任何时刻都不会出现"半个文件被当成正式副本"。死亡运行的临时对象在下一轮开头清理并计入运行记录。

**不做回滚**：回滚需要在崩溃后仍能可靠执行，而崩溃现场本身不可靠；顺序 + 幂等重跑更简单也更可验证。

### 3.4 索引只在整源成功后推进

`allowRemoteDelete` 依赖"上轮成功清单"来区分"本地删除"与"远端有但我们从未管理过的文件"。若某源有失败项仍推进索引，下一轮就会把失败文件当成"已备份过"从而可能误删远端。因此：整源零失败才写索引；部分失败时该源报 `partial`，下轮重算。

### 3.5 判定规则：宁可不删，不可错删

规划器只在这三种情况下认为内容变了：

| 情形 | 结论 |
|:--|:--|
| 远端大小不同 | 变了 → 归档 + 重传 |
| 远端摘要与本地不同 | 变了 → 归档 + 重传 |
| 远端无摘要、大小相同 | **不动**，报 `size-match-unverified` |

最后一行是实现中最容易写错的地方：早期版本把它当成"内容不同"，导致每轮都重传所有文件。备份工具的默认应该是保守——少一次上传是可接受的浪费，错删/错覆盖不是。

### 3.6 通过 JSON 报告的退出码表达状态

`run` 与 `verify` 用退出码 1 表示"跑完了但有问题"，JSON 报告才是权威结果。Harness 侧把"退出码非 0 且**无** JSON 报告"视为真正失败并抛出，避免把"配置缺失"误读为"空成功"。这是 harness 层单测专门覆盖的分支。

### 3.7 工具走子进程，而不是在主机内复用引擎

`vault_sync_*` 工具 spawn CLI 并解析 JSON：

- 同一份配置、同一份引擎、同一把锁 → cron 与对话里的行为完全一致；
- 主机进程不加载第二套状态，不会因为长上传阻塞事件循环；
- 超时/输出上限由 runner 统一约束（30 分钟、4 MiB）。

代价：每次调用 ~100 ms 进程启动，对分钟级备份可忽略。

## 4. 边界与未实现

- 双向同步、远端回写：明确不做。
- OSS 生命周期规则、`RestoreObject` 解冻：不做，交给控制台/`ossutil`。
- PDF 解析、OCR、全文索引：不做。
- 软链接：不跟随（`readdir` 只收普通文件），符号链接目录不会被遍历。
- 大文件：默认单文件上限 512 MiB、单轮 200 GiB，超出会跳过并在报告里说明原因，不静默丢弃。
- 并发：不同源之间当前串行执行（每源内部也串行，以保证归档先于覆盖）；`remote.concurrency` 已作为上限校验项保留。
- 逐次变更日志、跨日版本保留清理自动化：分别为刻意取舍与部署侧策略。
